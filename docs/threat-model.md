# Threat model - OWASP Top 10 for Agentic Applications (2026)

**System:** one self-hosted multi-agent gateway (18 configured agents: 14 conversational, 4 internal helpers) on a Windows PC, reached through Telegram and a personal WhatsApp
number, with file, web, browser, shell and scheduler tools; see [architecture.md](architecture.md).

**Assumptions.** Prompt injection cannot be fully prevented, so any agent that reads outside content (web, mail, documents, a
friend's message) may be hijacked. The owner's phone and messaging accounts are trusted and are the root credential. The PC's
admin account is trusted. AI coding sessions are useful but untrusted until a human approves their code.

**Assets.** Provider API keys and OAuth grants (business mail and drive); the owner's personal messaging identity; personal
data in agent memory; the PC itself (admin rights); the ability to send messages as the owner.

**Status keys.** *Implemented* = in force and verified by a job result. *Partial* = some paths covered. Evidence names the kind
of record in the project; finding ids (C/H/M/L) refer to the findings register.

| ID | Risk | How it applies here | Controls implemented | Evidence | Residual risk |
|---|---|---|---|---|---|
| **ASI01** | Agent goal hijack | Web pages, search results, mail and documents (via the Google tool), WhatsApp messages from admitted friends all reach agents that hold tools. | Owner-only allowlists on Telegram (DMs, groups, commands). WhatsApp chat-gate: per-chat trigger word, owner-only commands, every unreadable input dropped. Web fetch denied on every agent except a dedicated tool-poor "scout" agent. Injection cases in the eval suite. | Config read-back jobs; gate regression tests; eval run. | **High.** No complete fix exists. Indirect-injection canary tests through each ingest path are designed but not yet run (M14, open). |
| **ASI02** | Tool misuse and exploitation | The platform's default tool policy allowed everything: shell, scheduler, plugin management, config changes. | Default-allow replaced with per-agent denies: shell exec on 5 of 18 agents, the scheduler tool denied on 15 of 18, config/gateway tools on none, plugin and node tools denied globally. Exec approvals pinned to exact argument patterns. Browser behind a per-topic owner switch; the guard proves from its own inbound record that the owner started the run. | Policy jobs and restart checks; eval re-run (read-only auditor made 0 tool calls). | **Medium.** The CLI-based model runtime has no execution sandbox (H2); shell is still available on 5 agents (commands outside an allowlist need approval). |
| **ASI03** | Identity and privilege abuse | All agents run as one service account that owns every secret; it was also used as a desktop user with signed-in browsers. Several other accounts could write into its state. | Non-admin service account made a pure service account (no desktop/RDP logon, browsers and profiles deleted). State-dir ACLs rebuilt (323 entries, 0 failures). Gateway runtime, Python and plugins moved to admin-write-only dirs. SSH keys-only, tailnet-only. Owner MFA on messaging and provider accounts. Dashboard token rotated, step-up for dangerous phone actions. | Platform audit critical 50 -> 0; ACL and logon-right jobs. | **Medium.** One account still holds all agents' secrets (H1, accepted until a dedicated host); secrets are plaintext files behind ACLs and full-disk encryption (H4, open); one key per provider shared by all agents, no spend caps (M11, open). |
| **ASI04** | Agentic supply chain | Security vendors reported malicious marketplace skills as the main real-world attack vector for this platform in 2026; plugins run in-process; the ops repo itself is code that runs as admin. | No marketplace skills (registry disabled, bundled only). Custom plugins reviewed, installed admin-write-only with a SHA-256 baseline. Trusted launcher: every code change since the last approval is shown and needs a typed TRUST. Releases wait 24-48 h before upgrade; upgrades are staged and rehearsed. | Launcher install and update jobs; plugin hash baseline job. | **Medium.** Two official npm plugins load from a service-writable folder with no lockfile integrity; a one-off comparison with the registry tarballs matched and is re-run after upgrades (M23, open; version pinning risk-accepted, M8). |
| **ASI05** | Unexpected code execution | Agents with write access could change scripts that scheduled automations run in the gateway process, with no exec approval. Any agent shell could launch download tools. | write-guard extended: owner approval before an agent writes any script/code file or anything under a `scripts` folder. Per-account egress rules: shells, script hosts and download tools blocked off-box; runtime limited to TCP 80/443. Defender: 17 of 18 ASR rules in block mode, network protection on. | write-guard tests; firewall jobs (36 deployed, 34 after two removed; scope read back); ASR review after 6 days in audit mode. | **Medium.** No sandbox (H2). `.js/.ts` and data files are not gated by design; the prevalence ASR rule stays in audit because it would block a needed tool. |
| **ASI06** | Memory and context poisoning | A hijacked agent can write the attacker's instructions into its own persona file and keep them across sessions (public proof of concept exists). | write-guard: owner approval (allow once or deny, never "always") before writes to persona/instruction files; the prompt shows head and tail of the new text. Path canonicalisation closed a bypass (trailing dots, NTFS streams, 8.3 names, `@` prefix, look-alike letters). Persona file hash baseline; persona-only mirror in git for diffs. Stock instruction templates trimmed. | Guard regression tests (54 path cases); install and restart jobs; baseline job. | **Low-medium.** Daily memory notes are ungated on purpose (usability); poisoned notes are possible but do not change the instructions file. Writes made through a shell on the 5 exec agents bypass the guard. |
| **ASI07** | Insecure inter-agent communication | Agents share one gateway; a development agent could change live config, including another agent's channel access. | No agent holds the config/gateway or setup tools. The development agent's proposals reach the machine only through the human-approved job pipeline. Session isolation per channel peer. | Policy jobs removing those tools; config read-back. | **Medium.** One gateway is one trust boundary; there is no authenticated agent-to-agent messaging beyond the host's session isolation. |
| **ASI08** | Cascading failures | An upgrade or config change can restart the gateway and take every channel down; a model runtime can fail and silently fall back to another provider. | Rounds stop at the first non-zero exit; downtime jobs refuse to run unless the previous job's result says OK; rehearsal under the same account before any downtime; rollbacks exercised in advance; restore rehearsed; post-incident rules enforced by lint. Silent model fallback detected and fixed. | Post-mortem and rule set; rehearsal job that caught a destructive bug before downtime; restore rehearsal. | **Medium.** No per-agent cost, latency and failover view yet (M25, in progress). |
| **ASI09** | Human-agent trust exploitation | Approval prompts, launcher output and job text are what the human trusts; they can be spoofed (terminal escape codes) or approved by habit. | Runner and launcher print printable ASCII only and refuse jobs with control bytes; approvals are once-only; typed words (TRUST, KILL) instead of y/n for high-impact steps; relayed messages from other AI sessions never count as approval; downtime rounds go in their own round. | Launcher update job; runner tests. | **Medium.** Approvals arrive in the same messaging account the agent uses; approval fatigue is managed by process, not technology. |
| **ASI10** | Rogue agents | An agent may keep acting after it is misbehaving (ignoring stop commands is a documented failure of this class of system). | Out-of-band kill switch (stop; or stop + channels disabled by validated config patch so a reboot stays offline); the stop mode was drilled once (11 October, before later host changes), the channels-off mode and the dashboard button have not been. Daily scheduled audit, alerts to a private security channel on new criticals or a failed audit. Behavioural evals re-run after model or persona changes. | Kill-switch drill; alert delivery test; eval runs. | **Medium.** The in-dashboard kill path is not drilled yet; alerts go off-host but logs stay on the machine (no tamper-evident store); no tabletop exercise yet (L8). |

## Top residual risks (owner decisions)

1. **Shared host and account (H1, accepted).** The real fix is a dedicated host per trust boundary. Accepted for now with
   compensating controls (non-admin pure service account, egress rules, ASR, full-disk encryption, restore tested).
2. **No exec sandbox on the CLI runtime (H2).** Shell stays denied on 13 of 18 agents; moving the rest to a sandboxed runtime
   depends on the host decision.
3. **Secrets at rest (H4).** Plaintext files behind ACLs and full-disk encryption; migration to a secret store is open.
4. **Indirect injection untested (M14).** Canary tests are designed and waiting.
